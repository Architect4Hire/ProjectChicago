# ADR-0016: Event-Driven Audit Bounded Context Architecture

**Status:** Accepted  
**Date:** 2026-08-12  
**Participants:** Architecture team  
**Requirement Links:** [AUDIT-001..008](../requirements/lightweight-crm-product-and-system-requirements.md#audit-001); [DATA-020..023](../requirements/lightweight-crm-product-and-system-requirements.md#data-020); [PRIV-001..005](../requirements/lightweight-crm-product-and-system-requirements.md#priv-001)  
**Decision:** Implement the Audit bounded context as an event-driven append-only authority that consumes integration events through Azure Service Bus rather than allowing owning services to write audit state directly.

## Problem

AUDIT-001 requires every mutation to Clients, Projects, and Tasks to generate an audit event with specific fields and traceability. AUDIT-002 defines required audit fields including previous/new values and correlation metadata. DATA-020..023 require archival-over-deletion with privileged purge authority and retention documentation. PRIV-001..005 require minimized sensitive-data collection and authorization enforcement.

We must decide:

1. **Audit ownership**: Does Audit own the audit store exclusively, or do mutating services write directly?
2. **Ingestion path**: How do business mutations reach the audit trail without creating circular dependencies or bypassing transactional safety?
3. **Data minimization**: How do we capture enough context for auditability while avoiding unnecessary PII/sensitive-data duplication across services?
4. **Ordering and consistency**: What guarantees do we make about audit entry sequencing and freshness?
5. **Retention and purge**: Who may delete audit records, under what policy, and with what governance?
6. **Redaction**: Which fields are sensitive and must be stripped before audit persistence?

## Forces

- **Auditability** [AUDIT-001..008]: Every mutation must be recorded as an immutable, traceable fact
- **Transactional safety** [OUTBOX-001..005]: Audit events generated by mutations must not cause cascading failures or rollbacks
- **Append-only semantics** [AUDIT-004]: Audit records must never be modifiable through normal application workflows
- **Authorization** [AUDIT-005, PRIV-004]: Only privileged actors may access historical audit; ordinary users cannot modify it
- **Data minimization** [PRIV-001..003]: Avoid unnecessary copies of sensitive CRM data across service boundaries
- **Observability** [AUDIT-007]: Audit entries must link to distributed traces for troubleshooting
- **Retention governance** [PRIV-005, DATA-020..023]: Retention periods and purge authority must be documented before production

## Decision

### 1. Audit as Exclusive Append-Only Authority

**The Audit Service owns the audit database exclusively.**

- Owning services (CRM, Identity, Notification, Workflow) do not write directly to the Audit database.
- The Audit database is never shared with other services for joins, validation, or reporting shortcuts.
- Audit read queries go through the Audit HTTP API or approved observability surfaces; services never execute direct database access.

**Rationale:**
- Ensures append-only invariants are enforced in a single location.
- Prevents race conditions if multiple services attempt concurrent writes.
- Centralizes authorization checks for audit access (AUDIT-005, PRIV-004).
- Allows Audit to apply uniform redaction and filtering rules.

---

### 2. Event-Driven Ingestion Through Service Bus

**Business mutations emit integration events through their normal transactional outbox. The Audit Service consumes those events via Azure Service Bus and appends audit entries idempotently.**

```
Mutating Service (CRM/Identity/Notification/Workflow)
  ├─ Controller/Function ─> Facade ─> Business ─> Data layer
  │    └─ transaction: persist domain state + OutboxMessages record
  │    └─ emit past-tense event (e.g., ClientCreated, ProjectStatusChanged)
  │
  └─ Timer-triggered Function ─> OutboxRelay
       └─ Service Bus publish
            └─ Topic: ProjectChicago.Events (subscription: Audit)
                 │
                 v
            Audit Service (ProjectChicago.Audit.Functions)
              ├─ ServiceBusTrigger consumes event
              ├─ Facade ─> Business ─> Data layer
              │    └─ detect/register Inbox message (idempotency by MessageId)
              │    └─ construct AuditEntry from event + correlation metadata
              │    └─ INSERT into AuditEvents (append-only)
              │    └─ mark Inbox complete
              │
              └─ AuditDb stores immutable audit entry (no UPDATE/DELETE paths)
```

**Rationale:**
- Mutation and audit events remain transactionally atomic within the originating service.
- Outbox + relay ensures audit events are guaranteed delivery and survive transient failures.
- Audit processes events asynchronously, avoiding blocking mutating requests.
- Duplicate delivery (idempotency) is handled through Audit's inbox pattern.
- Audit never initiates reads/writes against other services' databases.

### 3. Required Audit Event Fields and Payload Structure

Every audit event recorded by Audit SHALL capture:

#### 3.1 Envelope and Correlation

- **AuditEntryId** (GUID): Unique audit record identifier, generated by Audit service
- **CorrelationId** (string): Traces the entire user request flow (HTTP request → Service Bus → downstream services); originates at gateway
- **CausationId** (string): Points to the immediate cause (parent message/request ID); allows following chains of causality
- **TraceId** (string): OpenTelemetry W3C trace context for linking to distributed logs; preserved from originating request or event
- **MessageId/EventId** (string): The integration event's own message ID from Service Bus; used for idempotency

#### 3.2 Entity and Action

- **AuditedAt** (DateTime UTC): Timestamp when the audit entry was written (may differ from the business event's occurred-at)
- **OccurredAt** (DateTime UTC): Timestamp when the business event actually occurred (from the originating service)
- **EntityType** (string): One of `Client`, `Project`, `Task` (or extended by future ADR)
- **EntityId** (GUID): The identity of the affected business entity
- **Action** (string enum): One of `Created`, `Updated`, `StatusChanged`, `Assigned`, `Reassigned`, `Completed`, `Reopened`, `Archived`, `Restored` (or extended)
- **ActionCategory** (string): Machine-readable category (`WRITE`, `TRANSITION`, `ASSIGN`, `ARCHIVE`) for filtering/reporting

#### 3.3 Actor and Source

- **ActorUserId** (GUID, nullable): The ID of the human user performing the action; `null` for system-initiated actions
- **ActorType** (string enum): One of `User`, `System`, `Service` (identifies whether the action was human-initiated or background)
- **ActorDisplayName** (string, nullable): Human-readable actor identifier (username or service name); for troubleshooting only, not authoritative
- **SourceService** (string): The service that published the event (`Crm`, `Identity`, `Notification`, `Workflow`)
- **SourceEventType** (string): The integration event contract name (e.g., `Crm.ClientCreated`, `Identity.UserActivated`)

#### 3.4 Changes and Context

- **PreviousValues** (JSON object, nullable): Before-state values for affected properties; structured as `{ "fieldName": value }` for common fields only
- **NewValues** (JSON object, nullable): After-state values for affected properties; structured as `{ "fieldName": value }`
- **SummaryDescription** (string): Human-readable summary (e.g., "Client lifecycle status changed from Lead to Prospect") for UI display
- **RawEventPayload** (JSON object): The complete integration event received from Service Bus (for forensics/reconstruction); redacted per rules

### 4. Field-Level Redaction Rules

**Sensitive data SHALL be stripped from audit payloads before Audit persistence.**

These fields are NEVER captured in `PreviousValues`, `NewValues`, or `RawEventPayload`:

- User passwords (any field named `password`, `pwd`, or similar)
- Authentication tokens or refresh tokens
- API keys or secrets
- Cryptographic material
- Session identifiers (except CorrelationId/TraceId, which are not secrets)
- Full SSN/tax ID (capture masked versions only if required for audit trail)
- Full credit card numbers (never store in audit)
- Raw private keys

These fields are captured **only** if explicitly required by audit scope and SHALL be flagged with `[REDACTED]` indicators in logs:

- Email addresses (capture, but log as `[REDACTED]`)
- Phone numbers (capture, but log as `[REDACTED]`)
- Full names (capture, but log as `[REDACTED]`)

When an integration event contains sensitive data, the originating service SHALL NOT include it in the event payload. Instead, send stable identifiers and let Audit resolve context through the Audit API if needed.

**Example:** When a Client's email is updated, the event carries `{ "clientId": "...", "emailChanged": true }` rather than `{ "clientId": "...", "oldEmail": "...", "newEmail": "..." }`. The Audit API can fetch the new email from CRM if an administrator specifically queries that client's audit history with appropriate authorization.

---

### 5. Before/After Value Capture

**Audit SHALL capture previous and new values for mutations according to these rules:**

1. **For CRM mutations (Client, Project, Task):**
   - Capture changes to fields like `Name`, `Status`, `Lifecycle`, `Priority`, `AssignedUserId`, `Description` (metadata/configuration fields)
   - Omit large object graphs (e.g., do not capture entire Project entities)
   - Use structured `PreviousValues` / `NewValues` (JSON objects keyed by field name)
   - Example:
     ```json
     {
       "Action": "StatusChanged",
       "PreviousValues": { "Status": "Active", "UpdatedAt": "2026-08-10T14:30:00Z" },
       "NewValues": { "Status": "Completed", "UpdatedAt": "2026-08-12T09:15:00Z" }
     }
     ```

2. **For Identity mutations (User activation, role changes):**
   - Capture role/permission changes
   - Omit passwords, tokens, and hashing internals
   - Example:
     ```json
     {
       "Action": "RoleAssigned",
       "NewValues": { "RoleId": "role-manager-guid", "RoleName": "Manager" }
     }
     ```

3. **For operations without clear before/after (e.g., Create):**
   - `PreviousValues` is `null`
   - `NewValues` contains the initial state (key metadata only)

### 6. Ordering and Sequencing Guarantees

**Within a single service's event stream:**

- Audit entries are recorded in the order events are consumed from Service Bus (at-least-once semantics).
- If the same event is redelivered due to transient failure, Audit detects it by `MessageId` and skips duplicate processing (idempotency through inbox pattern).
- Timestamp ordering relies on `OccurredAt` from the event (originating service's UTC time) and `AuditedAt` (Audit service's write time).

**Across services:**

- Absolute global ordering is not guaranteed; events from CRM, Identity, and Workflow may arrive at Audit out-of-order.
- Use `CorrelationId` + `TraceId` + `CausationId` to reconstruct causality (e.g., a single user request may spawn multiple events across services).
- UI audit history views SHALL sort by `OccurredAt` within a single entity's timeline and present service-specific audit streams separately when displaying cross-service actions.

---

### 7. Idempotency and Duplicate Handling

**Service Bus delivers messages at-least-once.** Audit handles duplicates:

1. Each integration event carries a `MessageId` (generated by the publishing service, deterministic for a given business event).
2. Upon consuming an event, Audit's Function checks its inbox table for a prior entry matching that `MessageId`.
3. If found and completed: skip and log as duplicate (no-op with telemetry).
4. If not found: create inbox entry, process, append audit record, mark inbox complete.
5. If processing fails after inbox check: Function fails (throws), allowing Service Bus to retry. Audit does not mark inbox complete.

This ensures idempotent audit append: redelivered events do not create duplicate audit entries.

### 8. Retention Policy and Purge Authority

**Define explicit retention requirements before production deployment** [PRIV-005, DATA-020..023].

#### 8.1 Default Retention Assumption (Placeholder)

Until superseded by security/compliance ADR:

- **Operational audit entries** (Client/Project/Task mutations): Retained for **7 years** (recommended for CRM compliance)
- **Authentication events** (user login, lockout, password reset): Retained for **2 years**
- **Administrative actions** (user role changes, audit access): Retained for **10 years**
- **Deletion/Archive events**: Retained indefinitely to preserve deletion proof

#### 8.2 Purge Authority and Process

- **Only Administrators** with an explicit `Audit.Purge` permission may initiate permanent deletion.
- **Purge requests** must be:
  - Logged with audit entry (who requested, when, which records)
  - Accompanied by a documented business/legal justification
  - Reviewed/approved by a second authorized role before execution
- **Purge is permanent** and cannot be undone; backups must be managed separately (IaC/deployment decision).
- **Hard delete** removes audit entries from the AuditEvents table; tombstone/logical delete is not sufficient for regulatory purge.

#### 8.3 Transparency and Compliance

- Audit SHALL maintain a separate `AuditAdministration` table recording all purge operations (who, when, what range, justification).
- Admins cannot purge the `AuditAdministration` table; this creates an immutable record of purge authority.
- Compliance audits may examine `AuditAdministration` to verify purge governance.

---

### 9. Separation of Operational Telemetry from Audit

**Project Chicago maintains two distinct observability channels:**

1. **Operational Telemetry** (Logs, Traces, Metrics via OpenTelemetry):
   - Short-lived (e.g., 90 days in a centralized log aggregator)
   - Includes diagnostic data (function call stacks, internal state, performance timings)
   - Redacted per PRIV-003 (no unnecessary PII in logs by default)
   - Used for troubleshooting, performance monitoring, and SRE response
   - NOT a durable business record

2. **Durable Business Audit** (AuditEvents table):
   - Long-lived per retention policy (7–10 years typical)
   - Records WHO DID WHAT WHEN to business entities
   - Includes before/after state and correlation to technical traces (TraceId)
   - Immutable and append-only by design
   - Used for compliance, forensics, and user-facing audit history

**Linking between channels:**
- Audit entries carry TraceId, allowing an operator to jump from an audit record to its distributed logs for forensic detail.
- Logs include CorrelationId/CausationId, allowing an SRE to jump to business context (e.g., "this timeout affected which client?").
- Neither logs nor audit should unnecessarily duplicate sensitive customer data; use stable identifiers.

## Consequences

### Positive

- **Audit integrity**: Audit owns its database exclusively; no service can bypass the append-only model.
- **Transactional safety**: Mutations and audit events remain atomic within the originating service; failures don't cascade to Audit.
- **Auditability in practice**: Every business mutation is recorded with traceability (correlation, trace, actor, timestamp, before/after).
- **Compliance-ready**: Redaction rules, retention policy, and purge governance support regulatory audit (SOC 2, data protection, financial audit).
- **Eventual consistency**: Audit may lag due to Service Bus processing, but all published events eventually land in audit (guaranteed by Outbox pattern).
- **Observability**: CorrelationId + TraceId links audit records to technical investigation.

### Negative/Tradeoffs

- **Audit latency**: Audit entries appear after Service Bus processing (typically milliseconds to seconds, not instantaneous).
- **Operational complexity**: Services must emit correct events; if a service forgets to emit an event, the audit gap is silent.
- **Storage cost**: Audit database grows with every mutation; retention policy must be managed.
- **Redaction maintenance**: Sensitive-field rules must be maintained as the data model evolves.

### Migration/Rollout

- Launch with default retention policy placeholder; finalize before production deployment (ADR or compliance review).
- Test idempotent event processing under Service Bus redelivery.
- Validate before/after value capture for key workflows (client creation, status change, assignment, archive).
- Implement audit API read endpoints and test query performance.
